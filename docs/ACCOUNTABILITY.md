# Accountability and recovery

## Sources, privacy and state

The engine reads bundled source-derived data via [core/data.ts](../core/data.ts); provenance and licences are in [DATA-SOURCES.md](DATA-SOURCES.md). [core/engine.ts:109](../core/engine.ts#L109) constructs the listing, evidence, decisions, escalations, actions, log and could-not-check list. Browser listing, preferences and eligible validated results use localStorage ([storage:248](../web/src/storage.ts#L248), [save:312](../web/src/storage.ts#L312)); restored results have permission gates rechecked. This is local app state, not an authenticated server audit database.

Live mode sends listing text to Gemini through the [server adapter:18](../api/gemini.ts#L18). The configured chain is `gemini-3.1-flash-lite` → `gemini-3-flash-preview` → offline rules; adapter defaults reverse the provider order unless overridden. Responses expose actual model/mode and fallback reason. The primary has 14 seconds and fallback up to 6 within a 20-second LLM budget, not a total HTTP latency guarantee ([adapter:4](../api/gemini.ts#L4)).

When a live API request has an extracted address but no known commute, the server may query OpenStreetMap Nominatim ([API:14](../api/analyze.ts#L14), [engine:135](../core/engine.ts#L135)). The [geocoder:14](../api/_lib/geocode.ts#L14) sends normalized address text with Waterloo/Ontario/Canada context and a generic app User-Agent; it sends no user identity or full listing and does not forward the browser IP. Address text still leaves our server. The in-process cache retains normalized queries and outcomes, including failures, and spaces request starts by at least one second per process. Fetch timeout is five seconds after any queue wait. There is no shared cross-instance rate limiter or durable lookup cache. Coordinates still need a bundled route within 600m; failure stays unknown. Explicit browser offline mode uses bundled rules/data without Gemini or Nominatim calls. The page separately loads Google Fonts ([index.html](../web/index.html)).

## Permissions and access control

[core/log.ts:12](../core/log.ts#L12) creates draft replies and evidence-card payloads automatically. Copy requires confirmation; ICS also requires feasible/tight commute, score below 0.3, no input refusal and zero unresolved escalations, including informational notes. [core/log.ts:28](../core/log.ts#L28) rechecks ICS conditions and rejects send_message, pay, sign and contact_landlord. Refused input blocks reply/copy; a scam-based REFUSE can still offer a safety reply. There is no user-account authorization layer; these are application capability rules, not protection against a user modifying client code.

## Confidence and escalation

[core/engine.ts:112](../core/engine.ts#L112) makes low-confidence fields (below 0.8), missing rent and verifier drops non-blocking notes. Missing address and injection indicators block. D2 low-confidence suspected violations (below 0.75) block; info topics remain ok with non-blocking notes. Scam scores from 0.3 through 0.7 create a blocking question. Unknown commute is a non-blocking note; infeasible commute causes HOLD. All unresolved notes still block ICS.

[D5:52](../core/engine.ts#L52) defaults to applies when residence/sharing evidence is absent; detected owner residence/sharing without explicit separate kitchen and bathroom produces may_not_apply and a blocking question. This is a screening assumption with a visible caveat, not verified legal applicability. [D6:78](../core/engine.ts#L78) refuses unprocessable input, score above 0.7, payment before viewing or detected sensitive identity/banking demands before viewing. Otherwise blocking questions, flagged clauses or infeasible commute cause HOLD; notes alone do not. [core/extract.ts:38](../core/extract.ts#L38) verifies spans and policy-sensitive values; quotation alone does not prove semantic correctness. See [DECISION-MAP.md](DECISION-MAP.md) for boundaries and covering tests.

## Log and recovery

[core/log.ts:7](../core/log.ts#L7) appends IDs, timestamps, actor, listing hash, available confidence/threshold and decision output; action entries retain inverse state. The hash is a simple noncryptographic fingerprint. The log is inspectable and append-only through normal core operations, not tamper-proof storage.

[core/log.ts:37](../core/log.ts#L37) restores reversible action state and appends an undo entry. It cannot retract clipboard contents or downloaded files. [core/log.ts:44](../core/log.ts#L44) keeps unsure answers unresolved and requires typed corrections for address/rent or commute questions. [markWrong:54](../core/log.ts#L54) rolls back generated actions in reverse order, validates/pins a correction, recomputes dependent state, reapplies the action gate and emits `{listing, decision_id, expected}` as a regression fixture. The fixture needs review and inclusion in tests; it does not train or persist itself. D7 policy cannot be overridden; a D6 correction cannot bypass a computed REFUSE.

Recovery path: inspect evidence → answer an escalation or supply a typed correction → inspect recomputed verdict/log → export and review fixture → add a regression test. Tests `correction rolls back actions, recomputes downstream and emits fixture`, `undo reverts the draft and preserves append-only history`, and `logs the recomputed verdict output after a correction` in [core.test.ts](../tests/core.test.ts) cover this path.
